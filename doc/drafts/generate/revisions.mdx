A catalog changes every year: cars come, cars go, prices move. Rljson does
not edit rows; it derives new ones. In a generated world, every model year
of a catalog is a cake of its own. Its slice ids build on the year before,
as in the [SliceIds](/guides/data_types/slices/) tutorial, its layers build
on the layers of the year before, and a [revision](/guides/data_types/revision/)
links each year to the next.

In this tutorial you generate three model years of one catalog, read what
each year adds and removes, resolve a derived layer, and follow the
revisions from the first year to the last.

You will learn how to:

- configure revisions of a catalog
- find the versions of a catalog in its manufacturer
- read derived slice ids
- resolve a derived layer with `base`, `add` and `remove`
- follow the revisions table

## 1. Set up the project

Create a project and install the generator and the core package:

```bash
mkdir car-world
cd car-world
echo '{ "type": "module" }' > package.json
pnpm add @rljson/generator @rljson/rljson
```

`"type": "module"` lets the application use ES modules and top-level `await`.
Now create the file `revisions.ts`. Each of the following steps adds code to
it: put the imports of a step at the top of the file, and its code below the
code of the previous step. The complete file is shown at the end.

<Aside type="note">
  Every layer of a cake uses the slice ids of its cake. So the layer of
  2027 names the slice ids row of 2027, and `BaseValidator` checks that it
  does, while `base` names the layer of 2026.
</Aside>

## What you have learned

- Every model year of a catalog is a cake of its own, and the manufacturer
  lists them all in `catalogsRef`.
- The slice ids of a year build on the year before, with `base`, `add` and
  `remove`.
- A derived layer stores only the assignments that changed, and resolving
  it follows `base` like `resolveSliceIds`.
- The revisions table links the versions by their hashes.
