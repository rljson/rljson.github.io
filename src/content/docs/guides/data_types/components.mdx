## 1. Set up the project

Create a project and install the core package and the hashing package:

```bash
mkdir car-catalog
cd car-catalog
echo '{ "type": "module" }' > package.json
pnpm add @rljson/rljson @rljson/hash
```

`"type": "module"` lets the application use ES modules and top-level `await`.
Now create the file `cars.ts`. Each of the following steps adds code to
it: put the imports of a step at the top of the file, and its code below the
code of the previous step. Steps 3 and 4 redesign the cars: they replace the
type `Car` and the table `cars` of the step before. The complete file is
shown at the end.

## 2. Create components

The example has three component types: manufacturers, wheels and cars. Each of
them gets a components table. For the cars, this step starts with the
simplest design.

### Manufacturers

manufacturers:

/>

A row is a flat or nested JSON object. Column names must be lower camel case,
like `founded`. A table is a JSON object with a few reserved fields:

| Field       | Meaning                                                                          |
| ----------- | -------------------------------------------------------------------------------- |
| `_type`     | The content type. For components tables, `components`                            |
| `_data`     | The rows                                                                         |
| `_hash`     | The hash of the table, calculated from all of its rows                           |
| `_tableCfg` | Optional: the hash of the [TableCfg](/guides/data_types/table-cfg/) of the table |

`hip`, short for _hash in place_, calculates the hashes and writes them into
the object you pass to it. Afterwards every row and the table carry a `_hash`:

<Snippet
  file="manufacturers.json"
  title="Output"
/>

A hash is a SHA-256 hash of the content, encoded as base64url and shortened
to 22 characters. The `id` of a row is a name for you and your application;
Rljson itself identifies a row by its hash. `ref` from `@rljson/rljson`
returns this hash: the reference that other rows store to point to the row.

<Aside type="note">
  A hash depends on nothing but the content. Hash the same values again, even
with the keys in a different order, and you get the same hash:

<Snippet
  file="components.spec.ts"
  region="same-content"
/>

`hip` also hashes nested objects. Each of them gets a `_hash` of its own,
and the hash of the parent includes it. That is why Rljson data is called
_deeply hashed_. This has three consequences:

- **Duplicates are easy to find.** Two rows with the same content have the
  same hash, so a store that is keyed by hash keeps them once.
- **Rows are immutable.** A changed row is a new row with a new hash.
- **Hashes need no server.** Every machine calculates the same hash for the
  same content, without any coordination.

</Aside>

### Wheels

A wheel refers to its manufacturer: it stores the hash of the manufacturer's
row in `manufacturersRef`:

<Snippet
  file="components.spec.ts"
  region="wheels"
  title="cars.ts"
/>

A column that refers to a row of another table is, by convention, named after
that table with the suffix `Ref`. `Ref` is the type of such a reference: a
hash. Since a hash depends on nothing but the content, the reference points to
exactly one version of the manufacturer, and it means the same on every
machine. The manufacturer is stored once, however many wheels refer to it.

A wheel needs no `id`. A row of the wheels table describes a kind of wheel,
and its hash identifies it.

`wheel0` and `wheel1` hold the same hash: both front wheels refer to the same
row of the wheels table. So each kind of wheel is still stored once, however
many cars use it.

The four columns do not end with `Ref`. The convention names a reference
column after its table, which works for one reference per table only. Four
references to the wheels need names of their own.

This design has its limits too. The columns fix the number of wheels at four:
a three-wheeler or a truck with six wheels needs other columns. And an
application that wants all wheels of a car has to read four columns one by
one.

The array combines the first two designs. Its length is the number of wheels,
like `wheelCount`, and each element can refer to a different wheel, like
`wheel0` to `wheel3`. A three-wheeler simply gets three elements.

The order of the elements is part of the content, and so of the hash: the
same wheels in another order make another row.

## 5. Validate components

Put the three tables into an Rljson object. Its keys are the names of the
tables. Then validate it:

<Snippet
  file="components.spec.ts"
  region="validate"
  title="cars.ts"
/>

`Validate` runs every validator you add and returns their errors, keyed by
the name of the validator. When no validator finds a problem, the result is
an empty object, and the application goes on.

`BaseValidator` checks the rules of the format. Among others:

- every hash matches its content
- table and column names are lower camel case
- table names do not end with `Ref`
- every table has a `_data` array
- the rows that layers, cakes, buffets and trees refer to exist
- tables with a TableCfg match it

It stops at the first rule that fails and reports the errors of that rule.

<Aside type="note">
  The base validator checks the references of a components table only for
  columns that a [TableCfg](/guides/data_types/table-cfg/) declares as
  references. Without one, it cannot tell that `manufacturersRef` and
  `wheelsRef` are references. The next step adds one.
</Aside>

The TableCfg declares every column of the cars. `manufacturersRef` holds one

## What you have learned

- A components table holds rows of JSON values in `_data` and declares its
  type in `_type`.
- `hip` writes a hash into every row and into the table. The hash is the
  primary key of a row.
- Equal content has an equal hash. A change creates a new row.
- A row refers to a row of another table by its hash, in a column that is,
  by convention, named after that table with the suffix `Ref`.
- Rows that refer to the same row share its data, which is stored once.
- An array of references refers to any number of rows, in a fixed order.
- `Validate` with `BaseValidator` checks the hashes, the names and the
  structure of an Rljson object.
- A TableCfg declares which columns are references. With it, the validator
  checks every reference, down to each element of an array.
